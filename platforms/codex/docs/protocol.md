# Protocol reference

vibecheck-linear-jev exposes eleven MCP tools. Every tool takes one typed `request` argument: `{"name":"project_status","arguments":{"request":{"project_id":"my-project"}}}`. The TypeScript boundary is `await new Board({store, linear}).call(toolName, request)` (`src/ledger/board.ts`), where `request` holds the fields directly and the result is plain JSON.

The plan, tasks, task state, claims and reports live in Linear. A local SQLite store (`state.sqlite3`) keeps what Linear has no place for: sessions, the plan key to issue map per revision, idempotency receipts, an issue cache, queued Linear writes (the outbox), completion plans, reconciler findings, and the verification history.

## Common fields

Every request includes `project_id`, a project key chosen by the coordinator (for example `audit-trail`). Mutations also include `request_id`; every mutation except `project_join` includes `session_id`. Unknown fields are rejected. Identifiers use letters, digits, `_`, `.`, `:`, `@`, `/` and `-`, start with a letter or digit, and are at most 200 characters. Short text is 1 to 500 characters; `goal`, `approach`, `report` and similar long text up to 20,000; documents and the project overview up to 200,000.

A `task_id` is a plan key (`SAVE-FATAL-5`) or a Linear issue identifier (`TA-42`); both are accepted everywhere, and an identifier matches in any case (`ta-42` is `TA-42`; identifier-shaped plan keys are written in upper case). Plan keys are 1 to 64 letters, digits, `.`, `_` or `-`. Titles are trimmed and kept on one line (line breaks and runs of spaces become one space). Report text is trimmed, and whitespace-only report text is no report.

Mutations are `project_join`, `plan_publish`, `plan_edit`, `plan_ack`, `issue_adopt`, `work_claim`, `work_update` and `project_update`. Each keeps an idempotency receipt for 30 days: repeating the same input with the same `request_id` returns the stored result without writing again; the same `request_id` with different input is a `conflict`. Receipts are scoped to the joining identity (project, vendor, runtime, external session ID) for `project_join` and to the session for every other mutation. A managed-mode dry run and an `adoption_required` answer are not stored, so the follow-up request runs; give it a new `request_id`. A `work_update` batch where any change failed is not stored either: repeat it with the same `request_id` and only the changes that did not land run again, the others are reported as applied.

Calls for one project run one at a time in a process. Every call first sends queued Linear writes (see Outbox) and resumes the project's pending completion plans (see work_update).

## Errors

MCP marks a failed call `isError: true` with a structured `error`: `code`, `message`, optional `details`.

| Code          | Meaning                                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `invalid`     | The request must change. Validation failures carry `details`, a list of `{field, message, type}`.          |
| `not_found`   | The request names a project, session, task, work or Linear object that does not exist.                     |
| `conflict`    | Current state disagrees: stale `expected_revision`, a claim another agent holds, a reused `request_id`.    |
| `forbidden`   | This session may not do it: not the coordinator, another project's session, or the project's mode refuses. |
| `unavailable` | Linear could not be reached, is rate limited, refused the key, or no key was found. Try again later.       |
| `internal`    | An unexpected failure. The message is always `Internal server error.`; details go to the server's stderr.  |

A Linear write rejected for its content becomes `invalid` with Linear's message. SDK-level schema errors may arrive as text-only errors with no structured content.

## project_join

Request: `repository`, `vendor`, `runtime`, `external_session_id`, `model` (required); `effort`, `parent_session_id`, `take_over_from`, `linear_project` (UUID, slug ID or project URL), `team` (team key), `adopt` (`as_is` or `managed`).

The first join of a project key on this machine registers it and its session becomes the coordinator; it must be a root session. The team is `team`, else `linear.team` in config, else the only team the key sees; with several teams and none named, the join fails with `invalid` listing the team keys. A session is unique per project by vendor, runtime and external session ID. Rejoining returns the same session and refreshes model and effort; its parent cannot change. A parent must exist in the same project. A root session takes over coordination by naming the current coordinator in `take_over_from`. The agent label is `agent:` plus the vendor lowercased with characters outside `a-z0-9-` replaced by `-`. Each join adds `repository` to the project's repository identities, which hooks use to find the project.

Without `linear_project`, no Linear project exists until the first `plan_publish`. With it, the key maps to that project, and the mode recorded in Linear decides how this machine treats it, so every machine reads the same answer:

- the `vibecheck plan` document's machine map says `"origin": "created"`: the tool created the project; it is linked in created mode;
- the `vibecheck policy` document's first line is the tool's `Adoption: managed. …` line (or the machine map says `"origin": "adopted"`): managed mode, and the dry run and confirm rules apply on this machine too (its first plan write is a dry run);
- nothing is recorded (no vibecheck documents, or a plan document whose map has no `origin`): the user's answer is needed. The existence of a plan document alone never makes a project `created`.

The plan map is rebuilt from the machine map in every case. Without `adopt` an unrecorded project writes nothing and the join returns:

```json
{
  "adoption_required": true,
  "project": { "linear_project_id": "...", "name": "...", "url": "..." },
  "summary": {
    "name": "...",
    "url": "...",
    "issue_count": 530,
    "readable_sections": { "goal": 328, "criteria": 430 },
    "issues_with_criteria": 430,
    "issues_with_other_headings": 329,
    "labels": [{ "name": "Area", "issues": 12 }],
    "milestones": ["M0 · ..."],
    "documents": ["..."]
  },
  "question": "May vibecheck update this Linear project to its own format? ...",
  "options": ["as_is", "managed"],
  "next_step": "Ask the user the question, then call project_join again with adopt ..."
}
```

Repeat the join with `adopt` and a new `request_id`. A later join with the other answer switches modes; switching to `managed` starts with a dry run again. `adopt` on a tool-created project is ignored. An `as_is` answer is kept on this machine only (as-is mode writes no documents), so another machine joining the same project is asked again.

Result: `session_id`, `coordinator` (boolean), `coordinator_session_id`, `agent_label`, `project` (`key`, `linear_project_id`, `url`, `name`, `adoption`), `plan_revision`, and `status`, a compact `project_status`.

## Adoption modes

`project.adoption` is `created` (the tool made the project), `as_is`, `managed`, or `pending` (waiting for the answer; every write is `forbidden`).

- `as_is`: the project is used as it is. Never edited: project fields, titles, descriptions, milestones, documents, existing labels, relations. Written: claim, report and verdict comments; the `vc:*` and `agent:*` labels on issues agents claim; state moves on issues agents claim, finish or release (both controlled by `AS_IS_WRITES_LABELS_AND_STATES`, default true, in `src/ledger/access.ts`). Issues are not assigned. Tasks are the existing issues, keyed by identifier. The policy comes from the project overview's `Goal` and `Rules` sections when it has them. `plan_publish`, `plan_edit` and `project_update` are refused (`forbidden`, `details.mode: "as_is"`); `issue_adopt` parses and writes nothing.
- `managed`: the first `plan_publish`, `plan_edit` or `issue_adopt` returns a dry run and writes nothing; repeating the same request with `confirm: true` applies it, and later plan writes apply directly. The machine keeps the hash of the last dry run it showed (the request without `request_id`, `session_id` and `confirm`): `confirm: true` on a request whose dry run was not the one shown returns that request's dry run instead of writing (its `message` says so), and becomes confirmable. Managed writes fill empty values (null, empty text or list, and priority 0, Linear's "No priority"; an estimate of 0 or any other number a person set is a value), add missing description sections while keeping every existing line, heading and checkbox, add `blocks` relations (including for identifiers already written under `Depends on`), add milestones, labels, issues, and the policy and plan documents. They never delete, archive, rename, overwrite a set value, remove a label or relation, or move an issue's state except through claims. A set value changes only when the request names it in `overwrite`, or when the tool itself wrote the current value and the plan changed it. Existing issue titles stay as they are (`MANAGED_PREFIXES_EXISTING_TITLES`, default false), so existing issues use their identifiers as task keys unless named in `overwrite` as `tasks.<KEY>.title`. A plan label of a single-select group on an issue that already has another label of that group is a set value: the dry run lists it under `skipped` as `labels:<group>`, and it replaces the old label (removed in the same update) only when `overwrite` names `tasks.<KEY>.labels`. The policy document records the managed answer in its first line, `Adoption: managed`, and the plan document's machine map records `"origin": "adopted"`.

## plan_publish

Coordinator only, not in `as_is`. Request: common mutation fields plus

- `expected_revision`: the current plan revision (0 before the first publish). Before any plan write (`plan_publish`, `plan_edit`, `issue_adopt`) the tool reads the plan document's machine map from Linear: a newer revision there (another machine published) refreshes this machine's map, and `expected_revision` must equal the revision Linear records, otherwise `conflict` (`details.actual`, `details.next_step: "plan_read"`): read the plan first, then repeat against that revision;
- `project`: `name` (required, at most 80), `summary` (one line, at most 255 characters as Linear counts them, in UTF-16 code units, so an emoji counts as 2; becomes the Linear description), `overview` (markdown, becomes the content), `icon` (a known Linear icon name from `src/linear/icons.ts` or a `:shortcode:`), `color` (`#rrggbb`), `priority` (0 none, 1 urgent to 4 low), `status` (`backlog`, `planned`, `started`), `start_date` and `target_date` (`YYYY-MM-DD`), `start_resolution` and `target_resolution` (`month`, `quarter`, `halfYear`, `year`), `labels` (project labels: `name`, `color?`, `description?`);
- `policy?`: `goal`, `rules[]`, `authorizations[]`, `stop_reasons[]`;
- `label_groups?`: `{name, color?, description?, labels: [{name, color?, description?}]}`, always single-select;
- `labels?`: ungrouped labels `{name, color?, description?}`;
- `milestones?`: `{code?, name, description?, target_date?}`; `name` is one line (line breaks and runs of spaces become one space, at most 80 characters); `code` defaults to `M1`, `M2`, ... by position; the Linear name is `<code> · <name>`;
- `documents?`: `{title, icon?, color?, content}`;
- `links?`: `{label, url}` (http or https);
- `tasks`: at most 2,000 task definitions (below);
- `update?`: `{health?, body}`, a project update posted with the plan (`onTrack`, `atRisk`, `offTrack`);
- `confirm?`: managed mode, apply the request whose dry run was shown last;
- `accept?`: problem ids of the readiness check (below) this request accepts;
- `overwrite?`: managed mode, field paths that may replace set values: `project.<field>`, `tasks.<KEY>.<field>`, `milestones.<CODE>.<field>`, `documents.<title>.<field>`. Project fields are named as Linear names them (`name`, `icon`, `color`, `description`, `content`, `statusId`, `priority`, `startDate`, `targetDate`); task fields as `title`, `priority`, `estimate`, `dueDate`, `projectMilestoneId`, `parentId` or a section field (`goal`, `criteria`, ...); milestone fields `name`, `description`, `targetDate`; document fields `content`, `icon`, `color`.

A task definition: `key`, `title` (required); `goal`, `criteria[]`, `rules[]`, `exceptions[]` (`{description, paths?, data_only?}`), `files[]`, `approach`, `depends_on[]` (keys or identifiers), `out_of_scope[]`, `report`, `original_behaviour`, `root_cause`, `evidence`, `parent` (key or identifier), `milestone` (code), `labels[]` (names), `priority` (0 to 4), `estimate` (integer), `due_date`, `status` (`pending` or `cancelled`), `supersedes[]`.

Everything is validated before the first write; a failing request writes nothing to Linear or the journal. Checks: icons, colors, summary length, dates; unique task keys, milestone codes and names, label names, document titles, link URLs; every `depends_on`, `parent` and `supersedes` reference resolves to a plan task or an issue of the project; no self references and no cycles in dependencies, parents, or both together; each task's milestone is declared; each task has exactly one label from every declared group, at most one label of any Linear label group, and every other label is declared or already exists. Plan labels are resolved against Linear's labels first: a label that already exists inside a Linear group stays in that group (it is never moved into a plan group), and the one-per-group rule is checked against the groups labels really have; a plan group named like an existing plain label, or a plan group label that is a Linear group, is an error naming both; `vibecheck policy` and `vibecheck plan` are reserved titles; a claimed task cannot be cancelled; tasks of the previous revision cannot be omitted (cancel them instead). New task keys that look like an identifier of the team (`TA-12`) are refused outside managed mode. Label and group names starting with `vc:` or `agent:` (any case) are reserved for the tool and refused, in label groups, labels and task labels.

What is written: the project with every field given, lead and member set to the key's user, team set; project labels; label groups and labels, reusing any existing label with the same name (team or workspace); milestones; documents; links; one issue per task titled `<KEY>: <title>` with the description sections, priority, estimate, labels, milestone, parent, due date, assignee = the key's user, state backlog (or canceled for `status: "cancelled"`); a `blocks` relation from each dependency to its dependent and a `related` relation for each `supersedes`; the `vibecheck policy` document when a policy is given (or in managed mode); the `vibecheck plan` document; the project update. Created objects carry client ids derived from the project and the object, so a publish retried after a failure finds what the first attempt created. When the `vibecheck plan` or `vibecheck policy` document was trashed, Linear refuses its old id as "already exists": the tool then uses a live document with that title, or creates the document with a fresh id and records it.

Republishing writes only what the plan changed since its previous revision, so edits people made in Linear to other fields survive. An issue's labels change by delta (each plan label added or dropped is added or removed on its own), never by sending a full label set, so labels added meanwhile (a claim's `vc:claimed` and agent label among them) survive; the tool's own `vc:*` and `agent:*` labels are never touched by a plan write. In created mode a milestone, priority, estimate, due date or parent the plan drops is cleared in Linear (priority to 0); in managed mode only when `overwrite` names it (`tasks.<KEY>.projectMilestoneId`, `.priority`, `.estimate`, `.dueDate`, `.parentId`). Description rewrites replace only the tool's sections; text before the first heading and under any other heading stays, and a ticked `Done when` box stays ticked while its text is unchanged. In created mode a dependency removed from the plan removes its `blocks` relation.

Result: `plan_revision`, `project_url`, `linear_project_id`, `task_map` (`{KEY: {identifier, issue_id, url}}`), `merged_with?`, `completeness`, `skipped?` (managed: fields that kept their value, `{object, key, field, old, new}`), `verification?`, `ready?` and `accepted?` (a first publish), `warnings?` (a later plan write), `sync: {pending}`.

**Readiness until the plan first passes.** A plan is fully developed before it reaches Linear. Until the plan has once passed readiness, every plan write (`plan_publish`, `plan_edit`, and in managed mode `issue_adopt`) runs every plan-time check before it writes anything; the first publish is the usual case, and in a managed project whose first writes were adopts the gate stays until a `plan_publish` or `plan_edit` passes. The time the plan passed is recorded as `readyAt` on the project row and as `ready_at` in the plan document's machine map, so a machine that joins later does not gate again. A managed `issue_adopt` that passes its own gate does not ready the plan. The checks: completeness (every field `completeness` lists, and the recommended `Kind` and `Area` label groups), plan-detail, task-duplicate, plan-coverage and brief-scope. While any problem is neither fixed nor accepted the call returns, without writing anything to Linear, recording a plan revision or keeping a receipt (the same `request_id` may be sent again once the plan is fixed):

```json
{
  "ready": false,
  "plan_revision": 0,
  "problems": [
    {
      "id": "completeness:project.icon",
      "check": "completeness",
      "object": "project",
      "field": "icon",
      "outcome": "missing",
      "reason": "the project's icon is empty"
    },
    {
      "id": "vibecheck.plan-detail:tasks.EXPORT-1:flagged",
      "check": "vibecheck.plan-detail",
      "object": "task",
      "key": "EXPORT-1",
      "outcome": "flagged",
      "reason": "the standard is too vague to check: ..."
    }
  ],
  "message": "The plan is not ready for Linear, ..."
}
```

Problem ids are stable while the problem stays the same: `completeness:project.<field>`, `completeness:milestones.<CODE>.<field>`, `completeness:tasks.<KEY>.<field>`, `<check>:tasks.<KEY>:<outcome>` (plan-detail), `vibecheck.task-duplicate:tasks.<KEY>.<OTHER>:<outcome>` (the two keys sorted, so the pair has one id whichever task was read first), `<check>:plan:<outcome>` (plan-coverage, brief-scope) and `judgment:unavailable`. A check's problem id ends with its outcome (`flagged`, `failed`, `review`, `unavailable`): a reading the judgment source could not make and a later flag of the same subject are different problems, and accepting one does not accept the other. The `recommended` label groups in `completeness` are advice and never a problem. Fix each problem in the plan, or name its id in `accept`; only when every problem is fixed or accepted does the publish write, and its result says `ready: true` with the `accepted` ids. An id in `accept` that names no current problem is `invalid`. A judgment source that does not answer never lets its checks pass: their problems have outcome `unavailable`, and with no judgment source at all the single problem `judgment:unavailable` stands for task-duplicate, plan-coverage and brief-scope; both block until accepted. When the checks are turned off in config (`ledger.verify: false`), no judgment is expected and `judgment:unavailable` is not raised; completeness still applies. The first publish's warnings stay in the response and the local history; nothing is posted to Linear. In managed mode the dry run carries the same `ready` and `problems`, and `confirm: true` writes only when they are fixed or accepted (adding `accept` does not change which dry run the confirm matches).

Later plan writes (`plan_edit`, and `plan_publish` after revision 1) are not gated: validation errors still refuse before any write, and the plan-time checks' outcomes that did not pass (`flagged`, `failed`, `review`) come back as `warnings` (problem-shaped) and are posted to Linear: a task's warning as a verdict comment on its issue, posted once per check, task and reason (a repeat for an unchanged task is not posted again); plan-wide warnings in a `## Warnings` section of the `vibecheck plan` document, since Linear has no comments on documents.

Two coordinators on different machines may publish the same revision at once (both pass the revision check). The plan document is re-read right before and right after it is written; when it holds another map for that revision, or a newer revision that misses a key of this request, the maps are merged into the next revision: this request's tasks, the other map's keys, and issues of the project that neither map names and that the tool created for a plan task (titled `<KEY>: …`, with the client id a plan task's issue gets). The merged map is written to the plan document and this machine's journal, `plan_revision` is the merged revision, and `merged_with: {revision, keys}` names the other revision and the keys this request did not have. The same scan runs after every plan write, merge or not: a project issue that a key of this machine's journals names (the same issue, titled `<KEY>: …`) or that the tool created for a plan task, missing from the map just written, is merged back at the next revision and reported in `merged_with` (the revision written, and the keys restored). A key is never mapped to another issue than its journal names. The other machine refreshes its map from Linear at its next `project_status` or plan write: a machine whose journal holds its current revision with another task map than Linear's refreshes from Linear.

`completeness` lists every fillable field left empty: `project` (`icon`, `color`, `summary`, `overview`, `start_date`, `target_date`, `priority`, `labels`, `links`), `milestones` (`{CODE: ["description", "target_date"]}`), `tasks` (`{KEY: [...]}` from `goal`, `criteria`, `files`, `approach`, `labels`, `labels:<group>`, `priority`, `estimate`; cancelled tasks are skipped). `recommended` is a warning, not an error: `{label_groups: ["Kind", "Area"]}` names the groups (matched by name, any case) the plan does not declare. Fill the gaps with `plan_edit`.

A managed dry run returns `{dry_run: true, plan_revision, changes: [{object, key, action, fields?}], skipped: [...], message}`. `changes[].fields` maps each field to `{old, new}`. The plan document's machine map carries `"origin": "created"` (the tool created the project) or `"adopted"`.

## plan_edit

Same rules as `plan_publish`. Request: common mutation fields, `expected_revision`, `operations` (1 to 2,000), `update?`, `confirm?`, `overwrite?`, `accept?` (a `plan_edit` before the plan has once passed readiness is gated like a first publish). Operations apply in order to the current plan, then the whole result is validated and written like a publish:

| `op`               | Fields                                                                                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `add_task`         | `task`: a task definition with a new key.                                                                                               |
| `update_task`      | `task_id` and at least one task field. An issue of the project not yet in the plan joins it, keyed by identifier, from its description. |
| `add_milestone`    | `milestone`; code defaults to the next `M<n>`.                                                                                          |
| `update_milestone` | `code`, `name?`, `description?`, `target_date?`.                                                                                        |
| `add_document`     | `document`.                                                                                                                             |
| `add_labels`       | `labels?`, `label_groups?`.                                                                                                             |
| `add_link`         | `link`.                                                                                                                                 |
| `set_project`      | `project`: any project fields; merged.                                                                                                  |
| `set_policy`       | `policy`; merged with the current policy.                                                                                               |

Fields given replace the plan's values; fields left out keep theirs. Result: as `plan_publish`.

## plan_read

Request: `project_id`, `revision?` (default current), `compare_to?`. Reads the local journal. Result: `project_id`, `plan_revision`, `metadata` (`actor_id`, `created_at`; absent for revision 0) and `task_map`, `{KEY: {...task definition, identifier}}`, plus `policy` when recorded. With `compare_to`: `compare_to`, `added`, `changed` (`{KEY: {before, after}}`) and `removed` (keys) instead of the map. A revision newer than current is `invalid`; one missing from this machine's journal is `not_found`.

## plan_ack

Request: common mutation fields and `plan_revision`. Records `acknowledged_plan_revision` and `acknowledged_at` on the session. A future revision is `invalid`; moving backwards is `conflict`; repeating a revision keeps its timestamp. Result: `plan_revision`, `session_id`, `acknowledged_plan_revision`, `acknowledged_at`.

## issue_adopt

Request: common mutation fields, `issue` (identifier or URL), `key` (plan key), `milestone?` (code), `confirm?`, `accept?`. Reads the issue description through the section aliases. A `key` shaped like an issue identifier of the team is refused (`invalid`) unless it is the adopted issue's own identifier (any case; written as the identifier). An issue the plan already keys is never re-keyed: `conflict` naming its key. The plan document write re-reads the document before and after writing and merges another coordinator's map of the same revision as `plan_publish` does (`merged_with`). In managed mode, until the plan has once passed readiness, it is gated with the checks a publish runs on a task: the adopted issue's missing sections (the fields publish's completeness asks for: goal, criteria, files, approach; not `depends_on`), its plan-detail wording, task-duplicate against the plan's other tasks, and `judgment:unavailable` without a judgment source; they are `problems` until fixed in Linear or accepted. Passing this gate readies the adopted task only; the next `plan_publish` or `plan_edit` is still gated. In `as_is` mode it writes nothing to Linear. Otherwise (coordinator only) it records the key for the issue in a new plan revision and the plan document, and in managed mode sets the milestone only when the issue has none. In managed mode before the first confirmed write it follows the plan rule: it returns a dry run (`dry_run: true`, `changes`, `message`, and the parsed task) and writes nothing until the same request comes back with `confirm: true`. A key already naming another issue is `conflict`.

Result: `mode`, `written`, `task` (`key`, `identifier`, `url`, `title`, `sections`, `unknown_headings`), `missing_sections` (of `goal`, `criteria`, `files`, `approach`, `depends_on`), `plan_revision`, `merged_with?`, `ready?`, `problems?`, `accepted?`, `verification?` (plan-detail).

## work_claim

Request: common mutation fields, `task_id`, `location?`, `replace_work_id?`, `force_release?`. A location has nullable `repository`, `checkout`, `branch`, `target_branch`, `base_commit` and `paths`. Paths are unique normalized repository-relative strings (no leading `/`, no `\`, no empty, `.` or `..` parts). Commits are full 40- or 64-character hex SHAs, stored lower-case.

The claim protocol (`replace_work_id` naming work this machine does not know follows the `force_release` rule below):

1. On this machine, one open claim per issue, decided in one SQLite transaction. Another open claim is `conflict` with `details.work_id` and `details.session_id`. `replace_work_id` names the open claim to replace; it is abandoned and its claim comment released. It may also name a claim comment with no live local work behind it, which is then treated as below. The local work row is written here, before the claim comment, with no comment id; a crash before the comment id is saved leaves it pending, and the reconciler settles it after 10 minutes: an open claim comment for the work completes it, none releases it.
2. Read the issue's comments. An open claim comment for other work:
   - whose work is open on this machine: `conflict` with `details.work_id`;
   - whose work is finished on this machine (complete, released, abandoned, conflict), or that a session of this machine wrote for work it never recorded: closed as `abandoned` (any session may), and the claim goes on;
   - whose work this machine does not know: `conflict` naming the holder (`details.work_id`, `holder_vendor`, `holder_session_id`, `last_activity`). When it has shown no tool activity (the claim comment, the `active <time>` on its claim line, or a later report comment) for 24 hours (`STALE_CLAIM_MS`), the conflict also carries `details.stale_claim: true`, `comment_id` and `next_step`, the exact retry: `work_claim` with `force_release: true`, which closes that comment as `abandoned (closed by work <id>)` and claims, or `replace_work_id` naming it, which closes it as `released (replaced by work <id>)` once the new claim comment is written. Before 24 hours both are `conflict`: a claim comment with recent activity is never force-released or replaced.
3. Write the claim comment (its claim line reads `open · active <ISO time>` from the start), add `vc:claimed` and the session's agent label, re-read the issue, move it to the in-progress state when it is not started, and assign the key's user when unassigned (not in `as_is`). When the re-read finds the issue completed, canceled or deleted (someone finished it while the claim was being written), the issue is not moved: our claim comment becomes `abandoned`, the labels the claim added come off, the work becomes `conflict`, and the call returns `conflict` with `details.reason: "task_closed"`.
4. Re-read the comments. Among open claim comments the earliest by Linear's `createdAt`, then comment ID, wins. When it is not ours, our comment becomes `released (lost claim race)`, the local work becomes `conflict`, and the call returns `conflict` naming the winning work in the message and `details.work_id`. The label stays; the winner holds it.

A completed or canceled issue cannot be claimed. When Linear stops answering after the claim comment landed, the claim is released by this machine: its work row says `released` before the queued edit closes the comment as `released` (and a queued removal takes `vc:claimed` off while no claim comment reads open), so the reconciler never reads that close as a lost claim; the call returns `unavailable`. Result: `work`, `issue` (`id`, `identifier`, `url`, `title`, `state`, `state_type`), `attention?` (as in `work_update`; a claim clears every event of the issue it returns except a `human_reply`), `verification?`, `sync: {pending}`.

A work record: `id`, `task_id`, `identifier`, `issue_id`, `session_id`, `status` (`in_progress`, `blocked`, `awaiting_integration`, `complete`, `released`, `abandoned`, `conflict`), `blocker`, `location`, `commit`, `integration_commit`, `claim_comment_id`, `predecessor_work_id`, `revision`, `created_at`, `updated_at`.

## work_update

Request: common mutation fields and `updates`, 1 to 100 changes, each naming a `work_id` once. Only the work's session or the coordinator can update it (another session repeating a finished completion is `forbidden` too), and only open work (`in_progress`, `blocked`, `awaiting_integration`) can change; work whose issue left the project was abandoned by the reconciler, so changing it is `conflict`. Work whose claim comment another machine or a person closed or deleted (attention `claim_lost`) was released; changing it is `conflict` with `details.reason: "claim_lost"`. The reconciler runs first; when Linear cannot be reached the update is judged from the cache. The whole batch is validated before any write.

A change that keeps the claim open and decides no completion (progress, `blocked`, `awaiting_integration`) writes Linear first (or queues the writes when Linear cannot be reached) and commits the local work row last, so Linear and the local store never disagree. A Linear failure that is not a lost connection (Linear rejecting a write) aborts that change before its local commit: the work stays as it was and the same change can be retried. A request with one change returns that failure as its error; in a batch each change applies or fails as a unit and the others go on. A batch where a change failed keeps only the hash of its input: the same `request_id` with the same changes re-applies what did not land, and with other content (for the failed change too) is a `conflict`. Comments a change creates carry ids derived from the session, the `request_id`, the work and the comment's purpose, so repeating a request after a failure never posts a comment twice, and two sessions reusing a `request_id` never share a comment.

Every change records activity on the claim. One that keeps the claim open re-reads the claim comment and rewrites only its claim line to `vibecheck claim · work <id> · open · active <ISO time>`, keeping the rest of the comment (a person's text included), and only while the comment is still this work's and open; a claim comment that was deleted or closed by someone else fails the change with `conflict`, `details.reason: "claim_lost"`, nothing written, and the work is released. Queued (Linear unreachable), the edit is sent only while the claim comment still reads open and names the work. A change that closes the claim writes its closing status the same way, on the claim line only.

Every state move re-reads the issue first. When it left the project (or Linear), its open work is abandoned (attention `removed`, claim comment closed) and the change fails with `conflict`, `details.reason: "task_removed"`, nothing else written. When a person moved it since the tool last read it, it is not moved and attention `skipped_move` reports it; a progress change or a release goes on, a completion does not (below). A move of a claim or a progress change queued because Linear cannot be reached is remembered, so the reconciler does not re-check the tool's own state when it lands; a completion's move is never queued.

**Completion plans.** `complete` (held or not), `release` and `handoff` run as a completion plan. Before the first Linear write the change records, in one local transaction, its verification entries, the decision (`verified`, `unverified` or `held`), the claim status it will write (`complete`, `released`, `handed off to work <id>`; none when held) and its ordered steps; the plan is keyed by the work, the session and the `request_id`. The steps then run in order, each idempotent and each checking in Linear when it runs that the issue is still in the project and the work's claim comment is still its own and open (or already carries the status the plan writes):

- complete, verified or unverified: move to done (only from the state the tool saw, or the state an earlier change's queued move of this machine brings it to), labels, the report and verdict comments, the claim comment closed as `complete`, `vc:claimed` removed (when no other claim is open), the local commit;
- complete, held: the claim's activity, `vc:held` added and `vc:verified` removed (`vc:unverified` added on an unavailable reading), the report and verdict comments, the local commit; the issue is never moved and the claim stays open;
- release: move to the first unstarted state (a skipped move is reported, the release goes on), labels off, the report and verdict comments, the claim comment closed as `released`, `vc:claimed` removed, the local commit;
- handoff: the target's agent label, the report and verdict comments, the successor's claim comment, this claim comment closed as `handed off to work <id>`, the local commit.

A failure stops the plan where it is and leaves it pending; nothing is queued for it in the outbox. The call returns the failure's error (`unavailable` when Linear cannot be reached, `invalid` for a rejected write) with `details`: `completion: "pending"`, `work_id`, `request_id`, `steps_done`, `steps_left`; in a batch the change's result is `{outcome: "failed", completion: "pending", error}`. The same plan, with the same decision (the checks never run again), resumes when the request is repeated with the same `request_id`, at the start of every later tool call for the project, and in `sync`. Only rejections count toward a cap: a plan Linear rejected five times (a rejected write, a missing object, a refused API key) resumes only when its request is repeated, and `project_status` lists it as attention `completion_waiting` naming the work, the `request_id` to repeat and the last error; an unreachable, failing or rate-limited Linear never counts, so such a plan resumes on its own once Linear answers. Repeating the same change with another `request_id` resumes it too; another change of that work is `conflict` (`completion: "pending"`, naming the request) until it ends. A repeat of a change whose plan already finished is reported as applied, never judged again: when the work is no longer open, and when it stays open (a held completion) as long as the work's latest plan is that finished one and nothing changed the work since its commit. `sync.pending_completions` counts the plans still pending.

The issue reads a plan makes go through the reconciler's change detection before they reach the local cache, so a person's move a plan sees first is still found (a re-check, `reopened`, `held_done_moved`); only the state the plan's own move brought is cached as the tool's own. While a completion plan of open work on this machine is pending, the reconciler does not re-check its issue: the plan owns that issue's outcome, and a re-check queued meanwhile waits until the plan ends (and is dropped when the plan's own move to done lands).

A precondition that no longer holds abandons the plan without moving the issue: the claim was lost (`conflict`, `reason: "claim_lost"`, the work released), the issue left the project (`conflict`, `reason: "task_removed"`, the work abandoned), a person moved the issue since the tool read it, or a person took the issue out of done after the plan's own move (`conflict`, `reason: "reopened"`, attention `reopened`: the work stays open with its claim, a closing edit already made is taken back, `vc:verified` comes off). A completion whose move is skipped is not complete: `conflict` with `details.reason: "skipped_move"` and `completion: "abandoned"`, the work stays open with its claim, no `vc:verified` is added, the done run is followed by a `review` entry so the task does not read as verified, and attention `skipped_move` follows. Every completion the checks passed that ends without reaching done, whether its own run or the reconciler ended it (a lost claim, a removed issue), gets that `review` entry, so status never reads it as verified. A handoff ended after its successor's claim comment landed has that comment closed as `abandoned` (queued; sent only while it still reads open and names the successor), so `vc:claimed` comes off under the usual rule and the task is free again. Report again with a new `request_id` once the issue is where it should be. While a plan is pending, the reconciler reads a claim comment that carries the plan's own closing status as this machine's close, never as `claim_lost`.

| `action`                | Fields                                                                                                                                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `progress`, the default | `status?` (`in_progress`, `blocked`, `awaiting_integration`, `complete`), `blocker?`, `location?` (merged; `null` clears; `paths` replaces), `commit?`, `integration_commit?`, `report?`. Explicit `null` clears a nullable field. |
| `release`               | `report?`. The work is released, its claim comment says `released`, the issue returns to the first unstarted state.                                                                                                                |
| `handoff`               | `handoff_to` (a session of the project), `report?`. The work is released, its claim comment says `handed off to work <id>`, a successor work for that session gets its own claim comment and agent label.                          |

`blocked` needs a blocker; `status: "complete"` with a `blocker` is `invalid`. `awaiting_integration` needs a commit and `target_branch` and marks the work as requiring integration; completing such work needs `integration_commit`. Changing the commit, target branch or repository clears earlier integration proof unless the same change supplies `integration_commit`.

Linear effects: a report becomes a report comment (`Done`, `Blocked`, `Progress`, `Released`, `Handoff`; a blocked change without a report posts the blocker). `blocked` adds `vc:blocked`, and `vc:needs-user` when blocker triage says the blocker needs the user (removed when triage says otherwise or the work leaves `blocked`). `awaiting_integration` moves the issue to the review state, or adds `vc:awaiting-integration` when the team has none. `in_progress` removes those again. A progress report the stalled check flags adds `vc:stalled`; the next one it does not flag removes it. Release, handoff and completion remove `vc:stalled` and `vc:needs-user`. `complete` runs the done checks first:

- held (a done check failed): the work and issue stay open, `vc:held` is added and `vc:verified` removed, a verdict comment gives the reason;
- otherwise the issue moves to the done state, `vc:blocked`, `vc:awaiting-integration`, `vc:stalled` and `vc:needs-user` are removed, the claim comment says `complete`, and `vc:claimed` goes when no other claim is open. It is verified, with `vc:verified` (and `vc:held` and `vc:unverified` removed), only when claims-done itself ran on the report and passed and no done check needed review or was unreadable. A done update with no report (claims-done cannot run and records `review`), one where claims-done was unavailable or turned off, or one with checks off completes the issue as unverified, with `vc:unverified` (and `vc:held` and `vc:verified` removed).

Label removal never depends on the cached issue. Linear refuses to remove a label the issue does not carry (`invalid`, "Label <id> is not on issue <id> and cannot be removed."); every removal the tool makes, sent, queued or in a plan, treats exactly that refusal as done. An unavailable check adds `vc:unverified` only to completions (and re-checks), never to other updates.

Verdict comments are posted for `failed`, `flagged` and `review` outcomes, and one `verified` comment when the completion is verified.

Result: `work` (changed and created work), `tasks` (`{task_id, identifier, status}`), `results` (one `{work_id, outcome: "applied" | "failed", error?: {code, message, details?}, completion?: "pending" | "abandoned"}` per change, in request order), `attention?`, `verification?`, `sync: {pending, pending_rechecks?, pending_completions?}`.

`attention` lists the pending events of the issues the call touched, including those found during it (by the outbox drain, a resumed plan, the reconciler or a move's re-read): `human_reply`, `skipped_move`, `claim_lost`, `removed`, `reopened`, `held_done_moved`, each `{kind, reason, entry_id, at, task_id, identifier, work_id?}`. An event is cleared only after a result returned it: a `human_reply` once a change with a report on that work answered it, a `skipped_move` once any change landed on the issue (or a claim of it), and `claim_lost`, `removed`, `reopened` and `held_done_moved` once a result showed them. Until then they stay in `project_status`.

## Checks

With a judgment source configured, mutations carry `verification`, a list of `{check, outcome, reason, entry_id, task_id?, work_id?, reported_status?, applied_status?}`. Without one, or with `ledger.verify: false`, no checks run and results have no `verification`.

| Event                                         | Checks                                                                                                                                                                                                                            |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `work_update` to `complete`                   | claims-done on the report against the issue's current goal, criteria and exceptions, with linked pull requests (merged, closed, draft, conflicts) as extra evidence; commit-paths; exception-check; parent-rollup; commit-honesty |
| `work_update` to `blocked`                    | stop-reason, deferral, blocker-triage                                                                                                                                                                                             |
| `release` with a report                       | gives-up, stop-reason, deferral                                                                                                                                                                                                   |
| `handoff`                                     | handoff-complete (no report is flagged)                                                                                                                                                                                           |
| progress with a report after three earlier    | stalled                                                                                                                                                                                                                           |
| `work_claim`                                  | claim-overlap against up to eight other open claims; a flagged overlap adds a `related` relation between the two issues (not in `as_is`)                                                                                          |
| `plan_publish`, `plan_edit`                   | brief-scope over the plan change, task-duplicate for added tasks, plan-coverage against the policy goal, plan-detail on added or changed tasks                                                                                    |
| `issue_adopt`                                 | plan-detail                                                                                                                                                                                                                       |
| an issue moved to done in Linear (reconciler) | claims-done and done-admits-unfinished against the current standard and the latest report comment, as one done run                                                                                                                |

Outcomes are `passed`, `failed` (a done check; the task is held), `flagged`, `review` and `unavailable` (no source answered; the change applies as reported). A done update without a report records claims-done as `review`. A task is verified only when its latest done run includes a passing claims-done; a flagged task-duplicate only comments, it never relates issues. plan-detail is decided by code: it flags a missing or very short goal, missing criteria, and goals or criteria with vague wording ("handle errors", "works properly", "as needed", "etc.", "TBD").

The history (`verifications` table) holds immutable entries: `verdict`, `unavailable`, `label` and `report`. Entries name the task by plan key or identifier.

## project_status

Request: `project_id`, `session_id?` (the calling session; it must belong to the project), `full?`, `include_map?`, `known_plan_revision?`, `task_ids?` (1 to 1,000 keys or identifiers; not with `full`). The reconciler runs first; when Linear cannot be reached the answer comes from the cache and `sync.error` says so.

Result: `next` (first), `project_id`, `plan_revision`, `project`, `attention?`, `tasks`, `counts` (by status over all tasks), `work` (open work), `sessions` (`id`, `vendor`, `runtime`, `model`, `parent_session_id`, `coordinator`, `acknowledged_plan_revision`, `last_seen_at`), `verification?` (full only: `{KEY: {reported, verified, reason, entry_id, at}}`), `plan_changed?` (when `known_plan_revision` is older), `task_map?` (with `include_map` or `full`), `sync` (`pending`, `pending_rechecks?`, `pending_completions?`, `error?`). `pending_rechecks` counts done re-checks still queued: over the per-run limit, or one that failed part-way and runs again next time; `pending_completions` counts completion plans not finished in Linear. After the reconciler, status refreshes this machine's plan map from the plan document when Linear records a newer revision or this revision with another map. A key this machine's journals know that Linear's map dropped (two coordinators wrote one revision at once) comes back then: when its issue is still in the project, titled `<KEY>: …`, the key is written back to the plan document with that same issue at the next revision.

`next` is a short ordered list of what the calling session should do now, each item with `kind` and `do` (the action, in a few words):

1. `attention` items about the session's own work, in attention order (at most 10): those naming a work record of the session, or with no work record a task it holds an open claim on. Each carries `attention` (the attention kind), `task_id?`, `work_id?`, `reason` and `entry_id`;
2. `claim`: each open claim of the session, with `task_id`, `identifier`, `work_id`, `status` (the work's), `verified?` and `blocker?`;
3. `available`: the next task the session could claim, with `task_id`, `identifier`, `title`, `milestone?` (code), `url` and `cancelled_dependencies?`. It is `pending` in Linear and not in the triage state (a triage issue is never offered), has no `vc:claimed` label and no open claim on this machine, every task its `Depends on` section or plan map `depends_on` names is complete or cancelled (a dependency naming no task of the project counts as not complete), every issue that `blocks` it in Linear is complete or cancelled (the relations of the candidates are read in order until one qualifies; an unreadable blocker counts as not finished; when Linear cannot be reached they are not read), and every child is complete or cancelled. A cancelled dependency counts as finished, and `cancelled_dependencies` lists such dependencies by key, with `do` asking the agent to check first whether the task still needs what they would have provided. Tasks are taken in the plan's milestone order (tasks with no milestone last), then plan order, then identifier;
4. `none_available`, only when there is no available task and the session holds no claim.

Without `session_id`, `next` holds only the `available` (or `none_available`) item. `project_join` returns its `status` with `next` for the joining session.

`tasks` maps each key to `identifier`, `title`, `status`, `state` (the Linear state name), `url`, `owner_work_id?`, `verified?` with `verified_reason`, and `missing_standard: true` when the description has no readable criteria. Compact status lists tasks that are not complete or cancelled plus tasks named in attention; `full` lists every task; `task_ids` lists only those.

Task status comes from Linear: `pending` (triage, backlog, unstarted), `in_progress` (started), `blocked` (started with `vc:blocked`), `awaiting_integration` (the review state or `vc:awaiting-integration`), `complete`, `cancelled` (canceled and duplicate). A started issue with open work of this machine reads `blocked` or `awaiting_integration` from that work's own state (and the review state), never from a `vc:` label someone else put on it.

`verified` follows one rule on every machine: the latest verdict recorded for the task's latest completion, whichever machine recorded it. Linear's tool labels and verdict comments are the shared evidence; this machine's done entries count only while they belong to the current completion (an issue's verdict floor moves when this machine sees it leave a completed state, reach one by someone else's move, get a new claim here, or carry a verdict label its current entries do not explain). Status reads this machine's latest done run above the floor, else the labels: `vc:unverified` reads unverified, else `vc:held` held (unverified on a complete issue), else `vc:verified` verified (`verified_reason` names the labels, `entry_id` is `issue:<identifier>`). A task that is not complete (and has no completion of this machine pending) never reads verified. When an issue leaves a completed state or is seen not complete with `vc:verified` / `vc:unverified`, the tool removes them (and `vc:held` unless the issue is claimed); `work_claim` removes all three; so a stale label never hides a reopen, and the next completion gets its done re-check. A failed re-check of an issue people moved to done reads `unverified`, not `held`.

`attention` (at most 50, in this order, after any `claim_lost` items) items carry `kind`, `check`, `reason`, `entry_id`, `at`, `task_id?`, `work_id?`, `needs?`, `urgency?`:

- `claim_lost` (listed first): another machine (`force_release`, `replace_work_id`) or a person closed this machine's open claim comment; the reason names the status it was closed with and who holds the issue now. The work was released here; stop working on it;
- `completion_waiting`: a completion plan Linear rejected five times waits for its request to be repeated; carries `work_id`, `request_id` (repeat `work_update` with it and the same change) and `last_error`;
- `held_done`: a done report failed its check and the task is open;
- `held_done_moved`: a person moved an issue to done while open work of this machine held its done report; the issue gets `vc:unverified` (never `vc:verified`) and the work stays open;
- `blocker` that needs the user or is urgent (others come later);
- `human_reply`: a person commented on a claimed issue after the claim's last claim or report comment (verdict comments and other tools' comments do not count); the reason quotes the comment;
- `reopened`: an issue left a completed state after it was complete, or after a pending completion plan moved it there (that completion was abandoned and the work stays open);
- `removed`: a claimed issue was archived, deleted or moved out of the project; its work was abandoned and its claim comment closed as `abandoned`;
- `write_dropped`: a queued Linear write was set aside after Linear rejected it five times; the reason names the issue, the kind of write and Linear's last error. Make the change by hand if it is still wanted;
- `skipped_move`: a state move was not made because a person moved the issue (or it left the project) after the tool read it, either when the queued move was finally sent or when the tool re-read the issue before moving it; cleared once a claim or update on the issue has returned it;
- `stalled`, `overlap`;
- `unverified_done`: a complete task whose latest done run is not verified (a check failed, needed review or could not be read, or claims-done did not run), including issues people moved to done;
- `flag`: other flagged checks on open work, open tasks or the plan, and a flagged commit-honesty from a task's latest done report;
- `missing_standard`: an open task whose description has no `Done when` criteria; done reports are judged on its description as a whole.

## work_history

Request: `project_id` and at least one of `task_id`, `session_id`, `path`, `branch`, `commit`; `limit?` (1 to 1,000, default 100). Selectors combine with AND. A path matches a claimed path, a path under it, or a path containing it.

Result: `project_id`, `work` (matching work records, newest last), `comments` (with `task_id`: the issue's Linear comments, `{id, created_at, kind: "tool" | "person", body}`, bodies clipped at 2,000 characters) or `comments_error` when Linear could not be read, and `verifications` (entries for the task or the matched work: verdicts with `check`, `version`, `outcome`, `reason`, `source`, `judged_by`, `readings`; reports with `action`, `status`, `report`; labels; unavailable readings).

## project_update

Request: common mutation fields, `health?`, `body?`. Not in `as_is`. Posts a Linear project update. Without `body`, it is drafted from verified status: tasks complete, and of those the ones verified now (a task that was reopened, or any task not complete, never counts as verified), tasks in progress and blocked, and the first five attention items. Without `health`, it is `atRisk` when a done report is held or a blocker needs the user or is urgent, else `onTrack`. When Linear cannot be reached it is queued. Result: `update` (`id`, `health`, `body`, `posted`), `sync`.

## Issue descriptions

H2 sections the tool owns, in this order: `What it is` (goal), `Report`, `Original behaviour`, `Root cause`, `Evidence`, `Files, lines and call sites` (bullets, paths in code spans), `Approach`, `Depends on` (`* TA-12 · <title>` or `Nothing.`), `Done when` (`- [ ]` checklist), `Rules`, `Accepted exceptions` (`* <description> (paths: \`a\`; data only)`), `Out of scope`. Parsing also reads `Goal`, `Acceptance criteria`, `Done criteria`, `Dependencies`, `Depends`, `Files`, `Files and lines`, `Owner report`, `Original-source behaviour`, `Root cause(s) found`, `Fix`, `Fix / approach`, `Non-goals`, in any case, H2 or H3, with a trailing colon or not. Text before the first heading and under other headings is never rewritten. Field text is escaped when written so it reads back exactly: a line that would read as a heading (`#`at the start or after one to three spaces, or a setext underline of`=`or`-`), a code fence or a checkbox bullet gets a leading `\`, a list item starting with `[x]` or `[ ]` gets a `\` before it, line breaks are written as LF, and an accepted exception's description has a `\` before each `(paths:` and `(data only` of its own; reading removes one such `\`.

## Documents

`vibecheck policy` (icon `Shield`): `Goal`, `Rules`, `Authorizations`, `Accepted reasons for stopping`. People may edit it; the checks and hooks read its current text, refreshed by the reconciler. `vibecheck plan` (icon `Page`): the tasks by milestone, then `## Machine map` with a JSON block `{"revision": n, "origin": "created", "tasks": {"KEY": "TA-1"}, "milestones": {"M1": "<id>"}}`. Only the JSON block is parsed; a second machine rebuilds the plan map from it at `project_join`. The map carries `"ready_at": "<ISO time>"` once the plan has passed readiness. The map read is the first valid JSON block after the document's last `## Machine map` heading (else the last valid fenced block); milestone names are one line, and names and titles render on one line with backticks escaped. The policy goal and items are escaped as issue fields are. `origin` is `created` when the tool created the project and `adopted` in a managed project; in managed mode the policy document's first line is the tool's `Adoption: managed. vibecheck may fill empty fields …` line, and only that exact first line counts. Together they tell a joining machine the mode (see `project_join`).

## Labels and comments

The tool's labels are ungrouped workspace labels created on first use: `vc:claimed` `#5e6ad2`, `vc:blocked` `#e5484d`, `vc:held` `#f76b15`, `vc:unverified` `#ffc53d`, `vc:verified` `#30a46c`, `vc:stalled` `#8e4ec6`, `vc:needs-user` `#e93d82`, `vc:awaiting-integration` `#0090ff`, and `agent:<vendor>` `#6e56cf`.

Every tool comment starts with one of the tool's headers (`**Claimed** by …`, `**Done**`, `**Progress**`, `**Blocked**`, `**Released**`, `**Handoff**`, `**vibecheck: <check> <outcome>**`) and ends with `— vibecheck · <vendor> · <model> · session <id>`; a comment is the tool's only when it has both, so a person's reply ending with a pasted footer is a `human_reply`. Claim: `**Claimed** by <vendor> (<model>)`, then `vibecheck claim · work <id> · <status>` (`open · active <ISO time>` with the last tool activity, written from the moment of the claim; plain `open` in older comments, `released`, `released (replaced by work <id>)`, `handed off to work <id>`, `complete`, `cancelled`, `abandoned`, `abandoned (closed by work <id>)`, `released (lost claim race)`). `abandoned` closes the claim of work the tool abandoned (the issue was archived, deleted or moved), and a claim comment closed because its work no longer lives; the `(… by work <id>)` forms name the claim of another machine that closed it. A claim line without the activity part reads as before. Report: `**Done**` (or `Progress`, `Blocked`, `Released`, `Handoff`) and the text. Verdict: `**vibecheck: <check> <outcome>**` and the reason. Tool comments are recognised by the footer and claims by their whole format, never by author, since every writer uses the same key: a comment is a claim comment only when its first line is `**Claimed** by …`, it holds the claim line, and its last line is the footer; a claim line quoted in a report, a verdict or a person's comment is never a claim. User text in report and verdict comments is escaped: a line that reads like a claim line or a footer gets a leading `\`.

## Reconciler

Runs at the start of `project_status` and `work_update`, and in `sync`. It reads the project's issues updated since its cursor less one second (so an update in the cursor's own millisecond is not missed; an issue whose cached copy is identical is skipped), refreshes the cache and the policy, and for each changed issue: one newly completed without a passing done check here gets a done re-check (claims-done and done-admits-unfinished on the latest report) only when it carries none of `vc:verified`, `vc:held` and `vc:unverified` and no tool verdict comment was posted after its latest completion, since verdicts are shared through Linear; an issue carrying `vc:held` (any machine's) or whose open work here held its done report is not judged again: `vc:unverified` is added (never `vc:verified`, and `vc:held` stays), attention `held_done_moved`; one that left a completed state is `reopened`; one archived or deleted while claimed has its work abandoned and is `removed`. Every issue with an open local claim is also read directly, since one moved to another project no longer appears in the project's pages: moved or deleted, its work is abandoned and it is `removed`. An abandoned claim's comment is closed as `abandoned` and `vc:claimed` comes off when no other claim is open (queued when Linear cannot be reached). The comments of issues with open claims are read directly, since comments do not change an issue's update time; a person's comment after the claim's last claim or report comment is a `human_reply`, and an open claim whose claim comment someone else closed or deleted releases its work here with attention `claim_lost` (a claim comment carrying the closing status of this machine's own pending completion plan is not lost). A completed state that the tool's own queued move brought is not re-checked, nor is an issue whose completion plan for open work here is pending (the plan owns its outcome; the re-check waits). A re-check that fails or cannot be read adds `vc:unverified`, removes `vc:verified` and posts a verdict comment; only one where both checks pass adds `vc:verified` (and removes `vc:unverified` and `vc:held`). In `as_is` projects a re-check of an issue no agent of this tool claimed (no local work and no claim comment) writes nothing to Linear: its result goes to the local history and the attention list only. A machine whose checks are off or whose judgment source is unusable writes no labels and no comments for a re-check either; its `review` entry stays local. The tool never moves an issue a person moved. At most `linear.reconcile.maxRechecks` (default 10) re-checks run per call; the rest wait. A re-check event is cleared only after the re-check is recorded and its writes sent or queued, so one that fails part-way runs again next time; both are counted in `sync.pending_rechecks`. The first sync of a project queues no re-checks.

## Outbox

Hooks never call Linear: they write verdicts locally and queue verdict comments and labels (a stop reply that claims the claimed task done while it shows work left queues `vc:held`). Hook label rows carry `skipIfCompleted: true`: such a row is not sent once the issue is completed or canceled (it counts as sent, nothing recorded as an error). Queued label writes carry the label name, not its id: the drain resolves the name against the team's labels, creates a missing `vc:*` or `agent:*` label, and drops a row naming any other label that no longer exists. A queued removal of a label the issue does not carry counts as sent; a queued removal of `vc:claimed` is sent only while no claim comment on the issue reads open. Queued state moves carry the state the tool expected the issue to be in (and its project): an issue already in the target state counts as delivered; one in another state or project is not moved, shown as attention `skipped_move`. A queued claim activity edit is sent only while the claim comment still reads open and names its work, and rewrites only the claim line. A queued `related` relation carries its client id. Queued creates carry their client id, so a resend after a crash cannot duplicate; Linear's "already exists" answer counts as sent.

The outbox is sent at the start of every tool call and by `sync`, oldest first, and one issue's rows in order: a row Linear rejects (invalid, not found, or an entity-level 403 / `FORBIDDEN`) holds back only the later rows of its issue while the drain goes on with other issues, and a network, server or rate-limit failure, or a key Linear refuses outright (HTTP 401 / `AUTHENTICATION_ERROR`), stops the drain without counting. Every rejection counts; a row Linear rejected five times is set aside with attention `write_dropped` (the issue, the kind of write, the last error). Completion plans are not queued writes: after the outbox, every call resumes the project's pending plans (`sync` every project's), except a plan whose issue still has queued rows waiting; a plan sends its issue's older queued rows before its own writes and waits while they cannot be sent.

A tool's Linear write that fails because Linear is unreachable, failing or rate limited queues that write and the rest of the call's writes; the result's `sync.pending` counts what waits. A write to an issue with older queued rows is queued behind them, so a call never overtakes them. The tool's `vc:*` and `agent:*` labels are created inside the write that adds them, so an outage while one is created queues the add instead of failing the call.

## Linear access

The key is a personal Linear API key: `LINEAR_API_KEY` (or the variable named by `linear.apiKeyEnv`), else `linear.apiKeyFile` (a 0600 file), else the interactive shell's environment, read with a 5-second bound. It is looked up on the first call that needs Linear; without it those calls are `unavailable`. Config `linear`: `team`, `apiKeyEnv`, `apiKeyFile`, `states` (`inProgress`, `review`, `done`, `canceled` names), `reconcile.maxRechecks`.

Tests only: `VIBECHECK_LINEAR_JEV_LINEAR_BACKEND=memory` with `VIBECHECK_LINEAR_JEV_MEMORY_FILE=<path>` runs against an in-memory Linear whose workspace is kept in that JSON file, shared by every process of a test. The memory backend is refused unless both are set.

## Transport and commands

`bun src/cli.ts` and the bundled `runtime/vibecheck-linear-jev.mjs` start the same server under Bun 1.3.14 or later. Options: `--version`, `--transport stdio|streamable-http`, `--database` (local store path), `--host`, `--port`, repeatable `--allowed-host`. Stdio is the default; HTTP defaults to `127.0.0.1:8765` with the endpoint at `/mcp` and needs `VIBECHECK_LINEAR_JEV_TOKEN` (bearer, no whitespace). `VIBECHECK_LINEAR_JEV_DB` sets the store path; the default is `$XDG_DATA_HOME/vibecheck-linear-jev/state.sqlite3` or `~/.local/share/vibecheck-linear-jev/state.sqlite3`. `VIBECHECK_LINEAR_JEV_PROJECTS` restricts both transports to a comma-separated list of project IDs.

- `vibecheck-linear-jev linear doctor`: where the key came from, the user and workspace it authenticates as, the team, the workflow states the tool will use, and rate-limit headroom. Exit 1 on any failure. The key itself is never printed.
- `vibecheck-linear-jev sync [--project ID]`: sends queued writes, resumes pending completion plans, and reconciles every linked project (or one), printing counts per project.

Claims do not lock checkouts or branches and do not prove an agent is still working. The commit-paths check reads a recorded commit from a readable local checkout with `git show`.
